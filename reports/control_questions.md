# Ответы на контрольные вопросы

## Практика 2
1. Прямые коммиты в main обходят ревью и проверки; отдельная ветка и PR упрощают проверку изменений.
2. GitHub Flow: создать ветку, внести изменения и коммиты, отправить ветку, открыть PR, пройти ревью, исправить замечания, слить и удалить ветку.
3. PR — обсуждение и проверка предлагаемых изменений на платформе. Merge — операция объединения истории Git, возможная и без PR.
4. Code Review — проверка изменений другим разработчиком для поиска ошибок и улучшения понятности решения.
5. Git распределённый: локально доступна история и можно коммитить офлайн. SVN централизованный: коммит направляется в репозиторий на сервере.
6. feat: обозначает новую функциональность по Conventional Commits.
7. git push -u origin имя-ветки отправляет ветку и задаёт upstream.
8. CLI нужен на серверах без GUI и для повторяемой автоматизации.

## Практика 3
1. Merge объединяет линии истории, при расхождении создаёт коммит с несколькими родителями. Rebase повторно применяет коммиты на новой базе. Для общей истории выбираем merge, для личной ветки перед PR допустим rebase.
2. Rebase изменяет хеши. У коллег остаётся другая история; несогласованный force-push приводит к расхождению и риску потери работы.
3. git rebase -i HEAD~5 предлагает план последних пяти коммитов. pick — применить, reword — изменить сообщение, edit — остановиться для правки, squash — объединить с предыдущим и отредактировать сообщение, fixup — объединить без сохранения сообщения присоединяемого коммита, drop — исключить. Есть также exec, break и другие служебные действия.
4. squash предлагает объединённое сообщение; fixup по умолчанию оставляет сообщение предыдущего коммита.
5. cherry-pick применяет изменение выбранного коммита поверх текущей ветки. Пример — перенос срочного исправления без экспериментальной функциональности.
6. Найти хеш через git reflog, затем git switch -c recovered ХЕШ. Reflog локален и хранится ограниченное время; это не резервная копия.
7. revert добавляет обратный коммит. reset --hard перемещает указатель, индекс и рабочее дерево, уничтожая несохранённые изменения отслеживаемых файлов. Для опубликованной истории обычно нужен revert.
8. Добавить remote через git remote add mirror URL. Для двух направлений push origin нужно явно добавить ДВА push-URL: исходный и зеркальный. Первый явный push-URL заменяет неявное использование fetch-URL. Команда git remote get-url --push --all origin проверяет конфигурацию.
9. Hooks — локальные скрипты на события Git. pre-commit может проверять форматирование перед коммитом, а commit-msg проверяет сообщение. В этой работе установлен commit-msg. Hooks не переносятся автоматически при клонировании; установка: git config core.hooksPath .githooks.
10. Forking Workflow: участник создаёт собственный fork, делает ветку, синхронизируется с upstream и открывает PR в исходный проект. GitHub Flow описывает короткую feature-ветку и PR; fork не обязателен.
